## 问题背景

原 `service/controller/controller.go::compareUserList` 以 UID 建立索引，但对相同 UID 的任意 struct 变化只把新值加入 `added`，没有把旧值加入 `deleted`。

实际调用链为：

```text
GetUserList
→ compareUserList
→ removeUsers(deleted old runtime tag)
→ addNewUser(added new identity)
→ UpdateInboundLimiter
```

因此 UUID、password、email/tag 或其他 protocol identity 变化时，新身份会尝试加入，旧 runtime identity 却可能继续认证。仅 `SpeedLimit`/`DeviceLimit` 变化也被错误当作 runtime add，且没有稳定区分 limiter-only update。

## 修复前确定性证据

先建立 UUID/password 回归测试，固定同一 UID 的旧值和新值。修复前实际结果：

```text
--- FAIL: TestCompareUserListReplacesChangedUUID
deleted = []api.UserInfo(nil), want old runtime user
--- FAIL: TestCompareUserListReplacesChangedPassword
deleted = []api.UserInfo(nil), want old runtime user
```

这直接证明旧身份未进入删除链。

## 根因

1. diff 只判断“UID 不存在或 struct 不同”，没有表达 add、delete、runtime identity replace、limit-only update 四类语义。
2. 使用 `reflect.DeepEqual` 比较 `api.UserInfo`，既无法表达字段语义，也在大列表中产生约每用户多次 allocation。
3. `map[int]api.UserInfo` 让完整含 string 的 struct 进入 map value，在 50k 用户场景造成额外 heap escape 和 GC 压力。

## 修改方案

`compareUserList` 现在返回：

```text
deleted
added
limitUpdated
```

分类规则：

- 新 UID：只进入 `added`。
- UID 消失：旧用户进入 `deleted`。
- 同 UID runtime/protocol identity 变化：旧用户进入 `deleted`，新用户进入 `added`。
- 同 UID 仅 `SpeedLimit`/`DeviceLimit` 变化：只进入 `limitUpdated`，不触发 runtime remove/add。
- identity 与 limit 同时变化：执行 delete-old/add-new；新值同时通过 added 集合进入 limiter update。

runtime/protocol identity 明确包含：

- `Email`
- `Passwd`
- `Port`
- `Method`
- `Protocol`
- `ProtocolParam`
- `Obfs`
- `ObfsParam`
- `UUID`
- `AlterID`

`UID` 是索引 key。除 `SpeedLimit` 和 `DeviceLimit` 外没有把现有 `UserInfo` 字段误归类为 limiter-only。

性能实现使用两个 O(n) 索引：

- `map[int]int`：UID → old slice index；
- `map[int]struct{}`：new UID membership。

从 old slice 按 index 读取 struct，避免把完整 `api.UserInfo` 作为 map value 造成逐用户逃逸。

## 已知风险

1. 本阶段修复 diff 语义和成功路径的 delete-old/add-new，但 xray-core user mutation 仍不是完整事务：批量 remove 部分成功、后续 add 失败时没有可靠 rollback。它对应独立的 runtime reload rollback 风险，不能写成本阶段已解决。
2. `nodeInfoMonitor`、`userInfoMonitor` 和 Close 的共享状态尚未同步；PHASE 4 必须建立 ownership，防止 diff 正确但并发 snapshot 不一致。
3. 删除用户后的 limiter/IP/bucket/stats cleanup 尚未完成，属于 PHASE 5/6；本阶段只确保 limiter 新值会收到 added 与 limit-only update。
4. UID 唯一性来自 panel 数据模型。本实现延续 UID 作为唯一 key；若外部 adapter 返回重复 UID，最后一个 old index/多条 new input 的行为未定义，应由 adapter validation 独立处理。
